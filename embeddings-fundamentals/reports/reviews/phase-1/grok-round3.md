Severity: high
File:line: embeddings-fundamentals/src/storage.rs:320
Description: `publish` reuses any existing `records.jsonl` whose non-empty lines all parse as `Record`, including an empty or whitespace-only file (count 0) and a file truncated to a valid prefix of lines. It does not compare `Checksum::of_bytes` with the active pointer's `records_checksum`. On that path it deletes the staged rebuild, returns `PublishOutcome::Reused`, and rewrites the pointer checksum to the damaged file. `process_source` then records `Succeeded` with `records_committed` left at 0. The next ingest sees the same revision id and a matching checksum, so `active_is_intact` is true and it returns `unchanged` before extraction. A missing file and unparseable bytes still quarantine and install.
Impact: A truncated but still-parseable active revision is committed as the live index. Later ingests exit 0, report `succeeded (unchanged)`, and never rebuild. Search serves the truncated or empty set for as long as that pointer remains.
Reproduction scenario or verifiable rationale: Ingest a source so revision R is active with a multi-record `records.jsonl` and pointer checksum C. Truncate that file to 0 bytes, or keep only the first complete JSON line. Re-ingest the same manifest and config. `publish` returns `Reused` (0 or 1 records), the pointer checksum becomes the truncated file's checksum, status is `Succeeded`, and `records_committed` is 0. A third ingest reports `unchanged` and still serves that truncated set. Replacing the file with `not json\n` still rebuilds. `a_damaged_active_revision_is_rebuilt_on_the_next_ingestion` only deletes the file and writes `not json\n`, so this path stays green.
Validation suggestion: When the existing directory is the revision the active pointer names, reuse only if the on-disk checksum equals `pointer.records_checksum` and every line parses. A checksum mismatch must quarantine and install the staged revision. Add a pipeline test that truncates `records.jsonl` to 0 bytes and to one valid line, then asserts the next ingest commits the full record count and a later ingest is unchanged only against that full set. A revision that is not the active pointer may still be reused when every line parses.
